Design document · draft 1

Slurm Queue Packer

A state-aware partition-placement supplement for Slurm. It does not replace the scheduler, reorder the queue, or touch fair-share — it decides only which partitions a job is allowed to land in, and it decides that from what the cluster looks like right now.

Cluster biocloud · 17 nodes · 3,872 CPUs · 22.8 TB Evidence 2,387,825 jobs, Nov 2023 – Sep 2026 Slurm 24.11.4

01 The measurement that started this

The high-memory partitions are not overloaded. They are being fed jobs that do not belong there.

Placement today is one rule in job_submit.lua:

if job_desc.min_mem_per_node / job_desc.min_cpus < 6000 then
    job_desc.partition = "zen5,zen3"      -- slim
else
    job_desc.partition = "zen5x,zen3x"    -- fat
end

It routes on the memory-per-CPU ratio alone and never looks at the absolute footprint. A job asking for 1 CPU and 32 GB has a ratio of 32,768 MB/CPU, so it is sent to the two high-memory partitions — 1,024 of the cluster’s 3,520 batch CPUs — where it queues behind other jobs that also do not need to be there. 32 GB fits on every node in the cluster.

Among the 38,342 that waited: 47.2% asked for a single CPU and 45.6% asked for 16–64 GB. Only 0.3% requested more than 1 TB, the point at which a zen3 node genuinely cannot hold them.

The conflation

Feasibility is absolute — does this job’s memory fit inside a node? Fit quality is a ratio — does consuming it leave the node’s remaining CPUs and memory in usable proportion? The current rule uses the ratio to answer both questions, and the ratio cannot answer the first one.

02 Diagnosis

Right on average, wrong at every individual moment

Over the 329 days since the zen* partition layout went in (571,248 jobs), demand above the 6,000 MB/CPU threshold accounts for 28.5% of CPU-hours. The two high-memory partitions hold 29.1% of batch CPUs. The static split is almost exactly right as a long-run average — and it still fails, because the mismatch is temporal, not structural. That is the entire case for making the decision dynamic.

The unit is the allocation-hour, and it is not the same as work

Everything the accounting database records is allocation: cpus_req × elapsed is the CPU-time a job was given, not the CPU-time it used. Under ConstrainCores=yes those cores are genuinely unavailable to anyone else, so allocation is the right unit for scheduling — but it is the wrong unit for throughput. A job that allocates 400 CPU-hours at 25% efficiency delivered 100 CPU-hours of work.

Why CPU efficiency is not in the objective

4,991,489 allocation-hours are held by jobs that are not using them — 2.2× what memory shape strands. It is tempting to score that. We deliberately do not. What matters to everyone else on the cluster is that the hardware is reserved and therefore unavailable; whether the owner is using it is their business. Nothing here can be 100% efficient — multi-step bioinformatics workflows have serial and I/O-bound phases that no scheduler can help — and scoring efficiency would penalise users for the shape of their science.

So the unit is the allocation-hour, for CPU and for memory, and that is the whole of it.

The one efficiency that does matter is time. Users overshoot their limits by roughly 7×, and admins extend limits by hand because a job killed at its limit is wasted work. That pessimism is what Slurm’s backfill plans against. A cohort-p95 estimate over (user, name, cpus, mem) — 1,848 cohorts covering 46.2% of jobs — shrinks the planning horizon to 21.7% of the declared limits, with 6.3% of jobs outliving the estimate and a median overrun of two minutes. Section 05 says what that is and is not good for.

03 Objective

Maximise work completed per unit time, not packing density

Packing is a means. The thing being maximised is throughput: how much data the cluster processes per unit time, subject to fair-share and a bounded wait for every class of job. Written as something a program can score:

Objective

Minimise queue time; maximise CPU and memory allocation-hours, weighted by node speed, subject to (a) fair-share ordering being left to Slurm, and (b) no job class exceeding its historical wait budget.

Three consequences follow immediately, and the third is the interesting one.

A CPU is not a CPU. A zen5 core does more work per second than a zen3 core, so stranding one costs more. This is already expressed in the PriorityTier ordering and the packer should not fight it.

Faster hardware is always preferable. A job’s work is fixed before it is placed, so finishing it on a quicker node returns both the cores and the memory sooner. That is already expressed in the PriorityTier ordering, and the packer does not fight it.

The idle-cluster case, and why it needs no special rule

When the cluster is empty, any placement is free right now, and yet placing carelessly is still wrong: a 1-CPU/900 GB job dropped on an empty zen3 node destroys that node’s ability to host anything else for the duration. The cost is not present waste, it is lost option value.

Make that the whole score. Let Φ(state) be the placeable capacity: the expected CPU-hours of future demand the cluster could still absorb, computed by greedily packing the measured demand distribution into the current free shapes. The cost of putting job j in partition p is

cost(j, p) = [ Φ(before) − Φ(after) ] − speed(p) × cpus(j)
             \_______ option value destroyed _______/   \__ work started __/

and the packer picks the feasible set that minimises it. No mode switch, no “busy vs. idle” flag, no tuning knob for cold start — the behaviour falls out of the same expression:

  • Idle cluster: Φ is large, so destroying it dominates. The packer places ratio-matched, exactly as you would by hand — it will not put a high-ratio job on an empty slim node, and it will not burn fat-node CPUs on jobs that do not need the memory.
  • Busy cluster: Φ is already near zero, so nothing is left to protect and the work term dominates. The packer fills whatever hole exists, which is the right behaviour when the future has already arrived.
  • Short jobs: a job that returns its resources within the hour barely dents Φ, so short jobs are admitted almost anywhere — which is what you want, and what backfill is already trying to do.

Φ is evaluated over a horizon rather than instantaneously, using predicted end times of the running jobs. That is what stops a 14-day job being placed into a hole that closes tomorrow.

04 Architecture

Decide slowly out of band, apply instantly in band

Slurm’s Lua job-submit plugin cannot see cluster state. Checking src/lua/slurm_lua.c at the 24.11.4 tag: it registers the logging helpers, time_str2mins, get_qos_priority, and the fields of the job record being submitted. There is no handle on running jobs, node occupancy, or the pending queue. The plugin also runs synchronously inside slurmctld — every millisecond spent there is a millisecond the controller is not accepting the next submission.

So the decision is precomputed by a daemon and the plugin only performs a lookup.

The table is emitted as Lua source — return {v=7,t={...}} — so the plugin parses it with the interpreter it already has. No JSON library, no new dependency, no parsing code to get wrong. It is keyed by (memory-per-CPU bucket × CPU bucket × walltime bucket), roughly 300 rows, and re-read only when its mtime changes. Everything in the plugin is wrapped in pcall; a plugin that throws would reject a user’s job.

Cadence

The scorer runs at 1 Hz. What it polls at 1 Hz matters more than the number: scontrol show nodes --json over 17 nodes is a small payload and is what determines the free shapes, so it is cheap enough to poll every second. squeue --json over a queue of thousands serialises every job record and takes a job-table read lock — at 1 Hz that would contend with the deeper backfill this design also asks for — so the pending queue is polled every 5–10 s. The policy table is written only when its content hash changes, so its mtime does not churn and the submit path re-reads it rarely.

Threads are for I/O overlap, not parallel compute. Scoring is roughly 300 buckets × 4 partitions × 17 nodes, single-digit milliseconds; throwing cores at it would achieve nothing, and the GIL would prevent it anyway. Four threads: a node poller, a queue poller, the scorer, and an actor that issues scontrol update under a hard rate limit — never rewriting a pending job’s partitions every second, which would churn slurmctld and re-fire the job_modify hook. The replay harness is where many cores genuinely pay, and it is parallel across windows and policies.

Constraint that shapes the design

For a job listing several partitions, Slurm evaluates them in PriorityTier order, not list order. The packer therefore cannot rank partitions per job — it can only choose the feasible set, and must prune to a single partition when it needs to override the tier. Tiers order; the packer gates.

Worth noting that biocloud’s tiers are zen5=10, zen3=9, zen5x=8, zen3x=7. Pure hardware speed would put zen5x level with zen5, since both are Zen 5. Placing zen3 above zen5x means the tiers already encode “save the high-memory nodes for jobs that need them” — a placement policy, not just a speed ordering.

05 Policy

Four mechanisms, in order of blast radius

Partition sets

Replaces the six-line rule at submit time with the precomputed lookup. Reversible per submission; no effect on work already queued.

Re-placement

scontrol update jobid=… partition=… on PENDING jobs only, never running ones. This is the manual operation being automated.

Cohort throttling

Caps how much of the queue one job shape may occupy. Covers job arrays via arraytaskthrottle, and non-array cohorts — workflow engines submitting thousands of separate but identical jobs — by narrowing their partition set instead.

Elastic limits

Moves MaxTRESPU on a flex QOS between a floor and a ceiling as cluster pressure changes, so limits relax over holidays and tighten when contended. Hysteresis and rate-limiting required. Highest blast radius — and, per the replay below, the binding constraint the moment placement is fixed.

Elastic relief: one job at a time, never a global limit

The caps exist to stop one user swallowing the cluster inside a minute. They are not a rationing scheme, so the right relief is not to raise them but to step around them, case by case, when capacity is genuinely idle.

Raising MaxTRESPU globally does the opposite. Every cap-blocked job across all 200 users becomes eligible in the same scheduling cycle; with 14-day limits and no preemption, whoever happens to be at the front holds that hardware for days. It recreates precisely the failure the cap prevents, at the moment you believed the cluster was quiet. It is also one irreversible decision taken from a single pressure estimate.

There are two ways to do that, and the replay says they trade against each other.

Global (the default). Raise MaxTRESPU and MaxTRESPA on the normal QOS, uniformly, while the cluster is persistently idle — then snap straight back the moment it is not. Every user faces the same number, so it is fair by construction, and fair-share keeps deciding who fills the room. The controller is deliberately asymmetric: five consecutive idle observations to step up by 25%, one busy observation to return to base. Slow to give and quick to take back is the safe direction, because jobs are not preemptible and a cap that is briefly too high can commit nodes for days.

Update (sqpd v1.1): a pulse, not a level. Staying raised for as long as the cluster is idle still lets one user who submits a large pool mid-window take up to twice the cap for days. sqpd now raises the caps only when pending jobs are held by the CPU cap (QOSMaxCpuPerUserLimit, MaxCpuPerAccount) and would fit in idle hardware, for 60 s, then returns to base and waits at least 5 minutes before the next pulse. The replay in tools/simulate.py still models the stepwise controller described above.

Per-job. scontrol update jobid=<id> qos=flex on one pending job at a time, into a QOS differing from normal only in its cap (Priority=0, UsageFactor=1.0, so relief never reorders the queue or changes what fair-share charges). More surgical — it can only ever affect one named job.

Per-job wins on throughput and on total wait, consistently, by two to three points of allocation and seven to fourteen points of waiting. Global wins on the thing this project set out to fix: high-ratio jobs wait less under global relief, decisively so under load (−74.2% against −44.4% in the busy window).

The reason is structural rather than incidental. Per-job promotion can only ever promote a job that can start immediately — that is what bounds its rate — and that condition systematically selects small, easy-to-place work over exactly the large high-ratio jobs that wait longest. Raising the cap for everyone has no such bias. Global is therefore the default, and per-job is kept as the more conservative option for a site that wants relief to touch one named job at a time.

Four properties do the safety work in either mode:

  • Asymmetric response. Global mode needs five consecutive idle observations to step up and one busy observation to snap back; per-job mode only ever promotes a job that can start immediately, which bounds its rate by the rate resources actually free up. Both make the cluster hard to swamp; a one-shot manual limit raise makes it easy.
  • A hard per-user ceiling of 2× the base cap, so even under relief nobody approaches monopolising anything.
  • The same option-value test the packer uses. A job is promoted only if it destroys no more placeable capacity than the cores it consumes (ΔΦ ≤ cpus). Without this the relief spends exactly the Φ the packer accumulated: in the busy window, ungated promotion took stranding from −20.8% to +57.0%. Gated, it is −4.6%.
  • The starvation guard and the relief are on the same side. A job that is both overdue and cap-blocked is the first candidate for promotion, since the cap is why it is overdue. An earlier design vetoed all relief while anything starved; that cost 4 points of allocation and 20 points of wait reduction for no real gain.

Demotion is free while a job is pending. What is not reversible is a promoted job that has started: it then holds its resources for its full runtime, up to 14 days. That one-way door is what the ceiling and the Φ gate exist to bound, and it is the argument for preferring short predicted runtimes among promotion candidates so the overflow drains quickly when demand returns.

Global mode needs no association changes and edits one QOS. Per-job mode needs one sacctmgr pass adding flex to the associations, since this site runs AccountingStorageEnforce=qos; its volume is modest and fully auditable at 1,186 promotions across a busy fortnight and 4,604 across a quiet one. Global mode spent 165–336 hours of each fortnight above the base cap, never above 2×.

Cohorts are 39% of the workload

Grouping the zen* era on (user, job_name, cpus_req, mem_mb, timelimit), 228,331 of 581,931 jobs belong to a cohort with 50 or more members. The largest single cohort is 69,589 individually-submitted jobs of 1 CPU and 4 GB from one user — not a job array, and therefore invisible to arraytaskthrottle. Cohort identity is that tuple; where scripts are byte-identical, script_hash_inx in the accounting database sharpens it further.

Runtime prediction, and what it is actually for

Forecasting which jobs will arrive and when means chasing a workload that changes as new tools appear. Forecasting how long the jobs already running will last is far better posed: a cohort-p95 over (user, name, cpus, mem) shrinks the horizon to 21.7% of declared limits with a median overrun of two minutes. No neural network; a sorted list per cohort, retrained in seconds, behind a one-method interface so a site that wants gradient boosting can swap it.

A negative result worth recording

The obvious use — feeding tighter horizons to backfill so it can overpack — buys almost nothing on this cluster. Replaying with predicted rather than declared reservation horizons moves allocation by at most 0.1%, at both EASY and conservative reservation depth. The reason is the table above: once placement is fixed there are only ~300 job-hours of resource-blocking left in a fortnight, so there is nothing for a tighter horizon to unblock. Pessimistic time limits are not what is costing biocloud its throughput. This would not hold on a cluster that is genuinely reservation-bound.

Prediction stays, for two other jobs. Φ’s horizon — so a 14-day job is not placed into a hole that closes tomorrow — and the elastic-limit controller, where deciding whether to raise a user’s cap now requires knowing when their running jobs will really release CPUs. Declared limits are 7× too long to answer that; cohort-p95 is 4.6× tighter.

One thing the packer will not do by default: reducing a pending job’s TimeLimit to the prediction would unlock genuine backfill headroom, but it kills the job if the daemon dies before extending it. That stays opt-in, behind an auto-extender that journals every original limit to disk.

Job arrival rates are used for exactly one thing: a coarse hour-of-week pressure index driving the elastic limits.

The starvation guard

A wait budget per job class, set from that class’s own historical p90. While a job is inside its budget the packer optimises for throughput. Once it exceeds the budget, the guard widens that job’s feasible set and narrows the sets of the cohorts competing with it, until it starts. This is a constraint on the optimiser, not a term in the score — throughput never gets to trade away a starving job.

06 Non-goals

What the packer must never do

  • Reorder the queue. Fair-share, contribution-weighted account shares, age and QOS priority stay entirely with Slurm. The packer changes where a job may land, never when it runs relative to others. This is what keeps the blast radius small and the fairness argument trivial.
  • Change a job’s requested CPUs or memory. Under cgroups that turns over-requesting into job failure.
  • Lower a job’s time limit. Predicted runtimes are used internally for scoring only. Setting --time-min would let backfill cut the real limit and kill long jobs; available as an explicit opt-in, off by default.
  • Touch running jobs. No requeue, no preemption, no cancellation.
  • Replace the scheduler. Backfill remains responsible for finding the holes. The packer only makes sure the right jobs are eligible for the right holes.

07 Scheduler configuration

Worth doing before any of this ships

bf_max_job_test is unset on biocloud, so it sits at its default of 500, while bf_max_job_user=100, default_queue_depth=2000 and MaxSubmitPU=2000. The manual is explicit that bf_max_job_test should be set much higher than bf_max_job_user. Backfill therefore never looks past the first 500 entries — and with 56% of jobs finishing inside five minutes, those 500 slots turn over constantly on trivial work while a high-memory job sits at position 900 without even an estimated start time.

This matters doubly for the packer, because backfill’s list is job-partition pairs: every extra partition in a job’s list consumes another slot.

08 Validation

Nothing reaches the live cluster until it has been replayed against three years of it

Trace replay

Per-node occupancy at any past instant is fully reconstructible from the accounting database: a job holds node_inx and tres_alloc between time_start and time_end, and is pending between time_eligible and time_start. That is enough to rebuild both the cluster and the queue, minute by minute, for the whole history — and it is how every number in this document was produced. The replay harness runs a candidate policy against the real arrival trace and reports stranded CPU-hours, wait-time distribution by class, and fair-share drift against the baseline of what actually happened.

Ordering constraint: relief must come second

The last two rows are elastic relief applied to the cluster as it is configured today, without the placement fix. It makes things worse: total wait up 17–18% and high-ratio jobs waiting 60–67% longer, in both the moderate and quiet windows. Promoting jobs into a badly partitioned cluster only lets more of them pile into the wrong partitions, and the jobs that lose are the ones already worst served.

Elastic limits are therefore not an independent improvement that can be enabled early because it looks cheap. They are safe only after placement is fixed — which is the same order the blast-radius argument gives, for a completely different reason.

Both policies cut waiting hard and both raise allocation, by more when the cluster is busy and there is headroom to take. They separate on stranding, and that is the case for Φ: the naive feasibility fix makes stranding worse in two of three windows — markedly so under load — because once every job may go anywhere, high-ratio jobs consume slim nodes’ memory and leave their CPUs unusable. The option-value term is what stops that, and it does most of its work exactly where the argument in §03 said it would: on the near-idle cluster, where Φ is large and worth protecting.

The packer is not uniformly better than the static rule on stranding — in the moderate window it is 12.6% worse. That is the trade being made: the static rule is good at avoiding stranding, by confining high-ratio jobs to two partitions, and pays for it in queue time and allocation. The packer gives some of that back for a 37% cut in waiting.

How far to trust these numbers

Simulated wait under the static rule against what the accounting database records: 32,252 vs 28,585 job-hours in the busy window and 10,920 vs 8,744 in the moderate one — close enough to be useful. In the quiet window it is 491 vs 5,032, badly off, because at 36% load the real queue is shaped by things this model omits: fair-share priority decay, bf_max_job_test, node drains and reservations. Comparisons between policies within one run are the usable output; absolute numbers are not calibrated.

Mechanism testing

A single-host test cluster with fake node definitions mirroring the real CPUs/RealMemory, SlurmdParameters=config_overrides, and sleep jobs. This proves plumbing only: the plugin sets the right string, the daemon’s updates land, the fallback fires, latency is acceptable.

Shadow mode on production

The daemon runs in observe mode: it computes every decision, writes a JSONL record with the job, the chosen set, the alternatives, the score, and the cluster state that produced it — and changes nothing. Two to four weeks of that is the face-validity check, and it is also the answer to “show me what it would have done”.

Then canary

Enforcement first for the re-placement of pending jobs, which is reversible and already done by hand today. Submit-time enforcement after that. Kill switch is a file: touch /etc/sqp/disable and the next submission uses the static rule.

09 Implementation

What exists, and what has actually been run

The daemon is written and runs. sqp/policy.py is the single implementation of the placement decision, imported by both the daemon and the replay harness, so the policy that is evaluated offline and the one that runs in production cannot drift apart — which matters more for a paper than for an operator.

Two deliberate choices are worth recording. The Slurm interface parses scontrol ... --oneliner key=value output rather than --json, because the JSON schemas move between releases — this site runs 24.11 in production and 26.05 on its test box — while the key=value form has been stable for years. And the policy table is rewritten only when the decisions change, not when the state does: an early version compared the rendered text, which embeds a timestamp, and so rewrote the file every second and would have forced the plugin to reparse on every submission.

How the plugin is tested without a cluster

tests/testcluster.sh starts a throwaway slurmctld as an unprivileged user on non-default ports, configured with the real node and partition topology — all 17 nodes, their true CPU counts and memory, the real PriorityTiers. No slurmd runs, so jobs stay PENDING; that is sufficient, because job_submit executes at submission and the partition it assigned is visible on a pending job. Node state is manipulated with scontrol update ... state=drain to make the cluster change underneath the daemon.

What that established:

  • The static fallback reproduces the current rule exactly, including routing a 1-CPU/32 GB job to the high-memory partitions — the behaviour this project exists to fix.
  • Decisions track cluster state. Draining zen5x and five of seven zen3 nodes changed a 16-CPU/64 GB job from zen5,zen5x,zen3 to zen5,zen3 and a 1-CPU/32 GB job from zen5x,zen3x to zen3x — same shape bucket, different answer.
  • Every failure path falls back and no submission is ever rejected. Table missing, table stale, table truncated mid-write, table replaced with non-Lua garbage, disable file present: each produced the static rule and a logged reason, and each job was accepted.
  • Write-on-change works. A 15-second run at 1 Hz produced three table writes, all of them real changes, none spurious — against twenty writes in twenty seconds before the timestamp bug was found.

Three bugs surfaced only under that test, and none of them would have been found by reasoning about the code.

The rendered table embedded a timestamp, so comparing rendered text rewrote the file every tick. The partition list came out ordered by score, so floating-point ties reordered an unchanged set and looked like a change; order is now canonical, which is free to choose because Slurm evaluates a multi-partition job in PriorityTier order regardless of list order.

The third one was worse than the bug being fixed

A 24-CPU / 2,200 GB job was rejected outright. Its shape bucket is open-ended — everything above 24,576 MB/CPU shares one bucket — so the table was built from a representative of 864 GB and answered zen3x, whose largest node holds 2,041,663 MB. The job needed 2,252,800 MB. The static rule this replaces would have accepted it, because it names both high-memory partitions unconditionally.

Bucketing had quietly discarded the absolute-footprint information that §01 identifies as the whole point. The table now carries each partition's largest node alongside it, and the plugin filters the looked-up set by the job's real size — recomputing feasibility across all partitions when the set it was given cannot hold the job, since pruning alone cannot recover from a representative that was too small. The correction is logged as refit so it is visible in the decision log rather than silent.

That is the argument for the test rig existing at all. The failure was invisible in the simulator, which works in exact job shapes rather than buckets, and invisible in the unit tests, which exercised the policy rather than the table.

Three of the 64 shape buckets describe jobs no node in the cluster can hold — 192 CPUs at 36 GB/CPU is 6.75 TB. Those resolve to the partition with the largest node rather than to an empty set, so the user gets Slurm’s ordinary “requested node configuration is not available” instead of a job with no partition. The behavioural test suite exists largely to catch that class of mistake.

10 Portability

Nothing above is specific to biocloud

Node and partition topology is discovered from scontrol show nodes --json and scontrol show partitions --json; the demand distribution and the runtime predictor are fitted from the site’s own sacct history. A site supplies one YAML file with policy weights and, optionally, a mapping of partitions into capability classes — which can also be derived by clustering nodes on memory-per-CPU.

Dependencies are the Python 3 standard library and the Slurm client binaries. Install is a package, one systemd unit, and adding JobSubmitPlugins=lua with the shipped job_submit.lua. Where --json is unavailable the daemon falls back to formatted squeue/sinfo output.

Open questions

  • How far ahead is Φ worth evaluating? Too short and it ignores the 14-day jobs; too long and it is dominated by prediction error.
  • Does cohort narrowing need a priority nice component, or is restricting the partition set sufficient on its own?
  • How should Φ treat the interactive partition, which is reserved and must not be packed?
  • Whether the demand distribution should be seasonal (hour-of-week) or a flat trailing window. The replay harness can answer this directly.
